Las cinco reglas básicas

  1. El producto no lleva IA.

    La IA es vuestra herramienta de construcción, no una funcionalidad de la aplicación. Nada de llamadas a modelos desde el producto.

  2. Solo cuenta main, el día 3 a las 17:30.

    Lo que esté en otra rama, en vuestro portátil o en un PR sin fusionar no existe para el jurado. Cuando llegue la hora, se congela.

  3. No se debilita la línea base.

    No modifiquéis .claude/settings.json, los hooks ni los workflows de CI. Vuestros ajustes personales van en .claude/settings.local.json; las reglas de denegación del fichero común siempre ganan.

  4. Las claves de API son personales.

    No se comparten, no se pegan en ficheros ni se suben al repo. Si se filtra una, avisad a la organización de inmediato.

  5. Todas las personas diseñan al menos un agente.

    Una skill o un agente propio por persona, con commits relevantes. Nadie es dueño único del orquestador.

Sobre el trabajo en GitHub

  • Las épicas las publica la organización en la wiki. No las editéis. Las historias las crea vuestro sistema, como issues nuevos con label historia.
  • main siempre en verde. Una rama por historia o change (us-7-cancelar-reserva) y PR a main con Closes #<historia>.
  • El CI tiene que estar en verde antes de fusionar. git push pide confirmación en Claude Code a propósito: es intencionado.
  • Los códigos de error y contratos que fije cada épica se usan tal cual.

Presupuesto y modelos

  • Modelos permitidos: haiku, sonnet y opus. Sonnet por defecto; Opus solo para decisiones difíciles y justificado en docs/evidencias/.
  • El crédito no se recarga. Por encima del 90 % lanzar un subagente pide confirmación.
  • Los bucles de agentes tienen tope de iteraciones (2–3 vueltas). Un bucle sin tope es un agujero en el presupuesto.
  • Al final, volcad vuestro coste con node .claude/hooks/budget.js report a docs/evidencias/.

Seguridad y permisos

La configuración común del evento (.claude/settings.json) se commitea para que todo el equipo y todos vuestros subagentes tengan las mismas reglas.

Se ejecuta sin preguntar

Node y npm (npm ci, npm test, npx vitest…), consultas de OpenSpec, Git local, leer y crear issues, descargar páginas de la documentación del stack y de esta wiki con WebFetch, ver runs del CI y editar el código y .claude/agents|skills|commands|memory.

Pide confirmación

git push|pull|merge|rebase|reset, rm -r, instalar paquetes concretos, openspec init|update, cerrar issues, crear o fusionar PR y gh api. Todo lo no listado también pregunta.

Está prohibido: sudo, ssh, wget, eval; forzar el push o publicar en npm; instalar paquetes globales; borrar issues o repos; leer .env*, claves (*.pem, *.key), ~/.ssh, ~/.aws o la configuración de gh; y modificar la línea base. El modo bypass permissions está desactivado.

Bonus: aplicar seguridad a vuestro propio sistema de agentes (qué puede hacer cada agente, qué herramientas tiene y qué hooks lo limitan) suma en el criterio C. El equipo ganador de la edición anterior lo hizo.

Honestidad de las cifras

Las cifras que cuente vuestro pitch (historias cerradas, tests, coste, número de agentes) tienen que coincidir con las del repo. En la edición anterior varios equipos perdieron puntos por números distintos entre el pitch, el README y el código. Los coaches auditan el repo antes de los pitches.

Convivencia

  • Es un evento de aprendizaje: preguntad, ayudad a otros equipos si os lo piden y compartid lo que aprendáis.
  • Cuidad el aula, el material y el trabajo de las demás personas. Un trato respetuoso es condición para participar.
  • Durante el evento se tomarán fotos para la comunicación de las entidades organizadoras. Daréis vuestro consentimiento de imagen en la inscripción.
